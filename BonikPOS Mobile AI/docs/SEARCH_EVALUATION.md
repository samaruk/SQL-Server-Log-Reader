# Medicine search evaluation

This document defines the labelled evaluation format for the medicine matcher, describes the datasets and the
method used, and reports results **measured by actually running** `tools/BonikPOS.VoiceSearch.Evaluation` on
2026-10-09 (Ubuntu 24.04 x86-64 container, 4 logical CPUs, .NET 10.0.12). Every number below is copied from the
report files in `eval/results/`. Nothing here was measured on a phone, with real speech, or with the real BonikPOS
catalog.

> **What these numbers are and are not.** The datasets were written or generated by the developer of the matcher.
> They are regression and robustness checks for the matching logic. They are **not** estimates of accuracy in a real
> pharmacy, with real customers, real recognition errors and the real ~20,000-product catalog. That requires the field
> evaluation in [EVALUATION_PLAN.md](EVALUATION_PLAN.md).

## 1. Dataset format (`bonikpos-search-eval/1`)

One JSON object per line (JSON Lines, UTF-8). Example lines from `eval/search/demo-authored.cases.jsonl`:

```json
{"id": "demo-001", "query": "Napa", "kind": ["ambiguous"], "lang": "en", "expect": {"products": ["DEMO-0001", "DEMO-0002", "DEMO-0003"], "decisions": ["Ambiguous"]}}
{"id": "demo-070", "query": "সেকলো বিশ মিলিগ্রাম ক্যাপসুল", "kind": ["bn-script", "bn-number-words"], "lang": "bn", "expect": {"products": ["DEMO-0010"]}}
{"id": "demo-173", "query": "make sure pro forty", "kind": ["asr-nbest"], "lang": "en", "expect": {"products": ["DEMO-0016"]}, "alternatives": ["maxpro forty"]}
{"id": "demo-214", "query": "napa 250", "kind": ["neg-strength-mismatch"], "lang": "en", "expect": {"products": []}, "note": "Napa exists, not 250 mg"}
```

| Field | Required | Meaning |
|---|---|---|
| `id` | yes | Unique case id. |
| `query` | yes | The text exactly as the recogniser (or the owner, when typed) produced it. Do not clean it up. |
| `expect.products` | yes | Product ids that satisfy the request; **any one** counts as correct. **Empty = negative case**: nothing in the catalog satisfies the request (unknown brand, a strength or form the brand does not have, not a medicine request). |
| `expect.decisions` | no | Acceptable `SearchDecision` values (`Confident`, `NeedsConfirmation`, `Ambiguous`, `LowConfidence`, `NoMatch`), e.g. `["Ambiguous"]` for "Napa" with no strength. |
| `kind` | no | Category tags for the per-category breakdown. |
| `lang` | no | `en`, `bn`, `banglish` or `mixed`. |
| `source` | no | `Voice` (default), `Typed` or `Correction`. |
| `alternatives` | no | Other recogniser readings (n-best / other language), searched as correction candidates. |
| `recognition_confidence` | no | Recogniser confidence (0–1); low values must cap the decision. |
| `speaker_decision` | no | `OwnerVoiceDecision` name (e.g. `Uncertain`); must prevent `Confident`. |
| `note` | no | Free text. |

Each report also records the dataset's SHA-256 and the catalog's description, size and SHA-256, so results are tied to
an exact catalog snapshot. Labels must be product **ids** from that snapshot.

### Labelling real data

1. Export the BonikPOS catalog snapshot (JSON, see [BACKEND_INTEGRATION.md](BACKEND_INTEGRATION.md)) and keep its SHA-256.
2. Take recogniser outputs from **consented** recordings (see EVALUATION_PLAN.md). Store the text, not the audio, in
   the dataset. Keep audio out of git.
3. A pharmacist labels each line with every product id that would correctly satisfy the request, or `[]`.
4. Run `search` (section 5) and keep the JSON report next to the dataset.

## 2. Metrics

- **Positive / negative case**: see `expect.products` above.
- **Top-1 / Top-5 accuracy**: share of positive cases whose first / any of the first five ranked products is correct.
- **False match**: the system presented a wrong product as *the* match: decision `Confident` or `NeedsConfirmation`
  and a wrong first result. Counted on all cases, so every `Confident`/`NeedsConfirmation` answer to a negative case
  is a false match. **Confident false match** is the subset with decision `Confident`.
- **Wrong product offered**: a false match, **or** an `Ambiguous` choice in which none of the offered options is
  correct. This is the stricter safety measure; the app never selects anything without the owner's tap, but an
  all-wrong choice is still a bad answer.
- **Negatives safely handled**: negative cases answered `NoMatch` or `LowConfidence` (candidates shown only with a
  "weak match – check" warning).
- **Correct but low confidence**: positive cases whose first result is correct but which were answered
  `LowConfidence`/`NoMatch`, i.e. the price paid for caution.
- **Missed positives**: positive cases answered `NoMatch`.
- **Matcher latency**: time inside the matcher per query on the machine above. **Not phone latency.**

## 3. Datasets and method

| Dataset | Cases | How it was made | Role |
|---|---|---|---|
| `eval/search/demo-authored.cases.jsonl` | 246 (213 positive, 33 negative) | Hand-written by the developer for the 55-product DEMO catalog: English, Bangla script, Banglish, number words (English and Bangla), typos, ASR-style word splits, recogniser n-best, generic names, quantities, strength/form disambiguation, decision caps, negatives. **Written before the search changes in this round.** | Baseline regression set. Its failures were then used to find bugs, so "after" numbers on it are **optimistic**. |
| `eval/data/synthetic-catalog-20k.json` (not committed; regenerate, SHA-256 `539870d4…0703d4`) | 20,000 products, 13,763 brands | `make-catalog --count 20000 --seed 20261009`: invented brand names, real generic names with common strengths/forms, 1–4 SKUs per brand, line extensions ("Plus", "XR", …), ~3% deliberately confusable brands, no Bangla names (as in a typical POS export). | Catalog at the target size. |
| `eval/search/synthetic-20k-dev.cases.jsonl` | 2,600 (2,000 / 600) | `make-cases --seed 7 --phrases A`: perturbations of catalog names (number words, Bangla script spelling, Banglish respelling, typos, word splits, generic+strength, brand+form) and negatives (invented names ≥ 2 edits away from every brand in spelling *and* in a simple sound-alike spelling; strengths/forms a brand lacks; everyday phrases from list A). | **Tuning split**: the one threshold chosen in this round was chosen here. |
| `eval/search/synthetic-20k-test.cases.jsonl` | 2,600 (2,000 / 600) | Same generator, `--seed 11 --phrases C` (phrase list C written after lists A and B had been inspected). | **Final held-out split**, evaluated once with the final code. 104 query strings also occur in DEV (mostly brand-only queries for the same products). |

Labels for the synthetic sets are computed by the generator from catalog values with its own parsing
(`SyntheticCaseGenerator`), independently of the matcher's parser, so the matcher's interpretation is not used to
grade itself.

**Process, in order (including what went wrong):**

1. Baseline: the matcher as committed before this round, run on all sets (`*-baseline.*`; built from the previous
   commit in a separate git worktree).
2. Bugs found on the demo set and the DEV split were fixed (section 4).
3. An early generator version labelled phonetically indistinguishable names (e.g. "Praiphac" vs catalog "Praifaac")
   as negatives, which is unfair for voice; the generator was revised to require two sound-alike edits. A second
   generator bug labelled "Brand 1000" as missing when the brand had "1 g". Both were fixed and DEV was regenerated.
4. Two earlier test splits (seeds 8 and 9) were looked at while debugging and were therefore **discarded**; the final
   test split (seed 11, phrase list C) was generated afterwards and evaluated once with the frozen matcher.
5. One threshold, `MinFuzzyConfirmNameScore`, was swept on DEV only ([dev-threshold-sweep.md](../eval/results/dev-threshold-sweep.md)).
   Rule: the smallest value with at most 3% wrong products offered on DEV negatives → **0.84**.

## 4. What changed in the matcher (each change answers an observed failure)

| Change | Observed failure that motivated it |
|---|---|
| `Ambiguous` only when the top score reaches `MinConfirmScore` (0.75); weaker results are `LowConfidence`. | "hello" was offered as a choice between two Seclo strengths at score 0.59. |
| Approximate (fuzzy) name matches below `MinFuzzyConfirmNameScore` (0.84, chosen on DEV) are shown only as weak suggestions. | Invented brands that sound like catalog brands were offered for confirmation. |
| Exact spelling beats a sound-alike; the spoken name beats a similar different name; the fuller spoken name beats a shorter one ("Napa Extend 500" must not become "Napa 500"). | "Daplai capsule" → Dapli, "Muten DS 40" → Muten 40 (Confident), "Danuuta 200" → Danuta 200 (Confident). |
| Form compatibility limited to oral liquids (syrup ≈ suspension ≈ solution); a compatible-but-different form is never `Confident`. Topical forms and injection/infusion are different products. | "Truchi cream" → Truchi **Ointment** (Confident). |
| Catalog forms like "Powder for Suspension" match both "powder" and "suspension/syrup". | "Zimax powder" ranked the tablet first. |
| Bangla transliteration keeps the inherent vowel of a word-initial consonant followed by a consonant and before a bare final consonant ("মন্টেয়ার" → "monteyar", "নেবানল" → "nebanol"). | Montair in Bangla script was not found. |
| Consonant-skeleton index for retrieval (vowel-only differences). | Vowel-dropped spellings shared no trigrams with the catalog name, so they were never retrieved. |
| Generic synonyms in parentheses and molecules of combinations are indexed ("Vitamin C (Ascorbic Acid)"; a combination molecule is ranked below single-molecule products). | "ascorbic acid" found nothing. |
| Dosage-form words inside a misheard name ("sir gel" → Sergel) are tried as part of the name and are then not treated as a requested form. | "sir gel twenty" found nothing. |
| "oh" is no longer read as zero. | "fax oh one eighty" lost the name. |
| Everyday conversational words may match a brand exactly but never approximately. | "ki khobor" → Kovaor (0.90), "thank you very much" → Muchim. |
| Recogniser alternatives (n-best; Whisper's other language when Bangla/English detection is uncertain) are searched as correction candidates; a product found only through an alternative is never `Confident`. | Mis-heard primary readings with a correct second reading. |
| No-match answers list up to three similar catalog names as "did you mean" buttons. They are not matches: tapping one starts a new search that still needs confirmation. | — (no-match usability) |

The remaining demo-set false match is "nexium 20" → **Nexum** 20 mg (`NeedsConfirmation`, shown as "Similar name …
please confirm"). A brand that is not in the catalog but sounds like one that is cannot be told apart by sound alone;
the owner's confirmation is the safeguard.

### Known remaining failure modes (from the reports)

- Unknown brands that sound like catalog brands are still sometimes offered for confirmation (6/189 on TEST),
  e.g. "Plasluin 500" → Pluslin 500 mg.
- Everyday phrases not in the conversational word list can still produce an all-wrong `Ambiguous` choice (6/30 on the
  unseen phrase list C; none were false matches).
- Recogniser splits whose first fragment is a filler word ("do", "to") lose that fragment ("to mir four hundred").
- A Bangla-script brand spelled like a number word ("জিরো") is read as a number.

## 6. Running it

```bash
cd "BonikPOS Mobile AI"
dotnet build tools/BonikPOS.VoiceSearch.Evaluation -c Release
E="dotnet tools/BonikPOS.VoiceSearch.Evaluation/bin/Release/net10.0/BonikPOS.VoiceSearch.Evaluation.dll"

# demo catalog
$E search --cases eval/search/demo-authored.cases.jsonl --catalog demo --out eval/results/demo.json --md eval/results/demo.md

# 20k synthetic catalog (deterministic; SHA-256 539870d42230de346e65767a4088c581a1d815216bc63179aa9cba02dc0703d4)
$E make-catalog --out eval/data/synthetic-catalog-20k.json --count 20000 --seed 20261009
$E search --cases eval/search/synthetic-20k-test.cases.jsonl --catalog eval/data/synthetic-catalog-20k.json --md test.md

# your own catalog export and labelled cases
$E search --cases my-cases.jsonl --catalog my-catalog.json --out my-report.json --md my-report.md
```

Options: `--min-candidate`, `--confident`, `--margin`, `--min-confirm`, `--min-fuzzy-confirm` override thresholds;
`--all-cases` lists every case in the JSON report (default: failures only). `build_demo_authored.py` regenerates the
demo set.

## 7. Limitations

- Synthetic brand names follow the generator's syllable rules, not the real distribution of Bangladeshi brand names,
  and the perturbations are the developer's model of recognition and typing errors, not measured recogniser errors.
- Latency was measured on an x86 container. Phone CPUs are slower; use the in-app benchmark
  ([BENCHMARKS.md](BENCHMARKS.md)) on real devices.
- Thresholds may need re-tuning on the real catalog: run the sweep on a labelled DEV set from real data and keep a
  separate held-out set.
